# Requirements

**Status: VALIDATED — every row below is VALIDATED (owner delegation of 2026-11-23; details in ADR-0001 to ADR-0035). A row added later starts PROPOSED until the owner validates it.**

Each requirement has a stable identifier. Agents must reference these identifiers in their plans, commits and reports. Identifiers are never reused: removed requirements are listed under [Retired identifiers](#retired-identifiers).

Priorities follow MoSCoW: **Must**, **Should**, **Could**. "Won't (for now)" items belong in `docs/vision.md` as non-goals. A Should or Could requirement is binding once its feature is scheduled: it is implemented as written, not reinterpreted.

The traceability matrix (requirement → decision → test) is in [`traceability.md`](traceability.md). The few questions still open are in [`open-questions.md`](open-questions.md).

## Game loop

Source: [ADR-0001](decisions/0001-technical-baseline-and-conventions.md) (principles), [ADR-0017](decisions/0017-fixed-step-game-loop.md), [ADR-0031](decisions/0031-runtime-defaults-loop-calibration-inbox-scenes-platform-lifecycle.md). The text of REQ-LOOP-004 to REQ-LOOP-006 is the ADR-0001 principle, unchanged; REQ-LOOP-007 to REQ-LOOP-012 make it precise.

| ID | Requirement | Priority | Status | Expected verification |
|---|---|---|---|---|
| REQ-LOOP-001 | The game loop has a contract independent of its implementation. | Must | VALIDATED | Contract tests. |
| REQ-LOOP-002 | Several loop implementations can be provided. | Must | VALIDATED | Tests with a controllable clock and scheduler. |
| REQ-LOOP-003 | Update and render are distinct concepts. | Should | VALIDATED | Execution order verified by test. |
| REQ-LOOP-004 | The default implementation is independent of machine power and frequency. | Must | VALIDATED | Same simulation and same final state for an identical simulated time. |
| REQ-LOOP-005 | The default loop combines frameskipping and extrapolation to adapt presentation to the available time. Frameskipping may drop a presentation, never arbitrary simulation computations. | Must | VALIDATED | Tests of cadence, render skipping and extrapolation. |
| REQ-LOOP-006 | An extrapolation greater than 1 must not reduce simulation accuracy; an extrapolated state is never reused as input of the next simulation step. | Must | VALIDATED | Tests showing the simulated state is always computed from the reference simulation time/scheme, without integrating the extrapolated state. |
| REQ-LOOP-007 | The default loop advances the simulation by a fixed step (default 60 Hz, configurable) from an abstract monotonic clock, using an accumulator and catch-up; the presentation factor `alpha = accumulator / step` is always in `[0, 1)` (ADR-0017). | Must | VALIDATED | Controllable-clock tests: exact number of updates for a given elapsed time, `alpha` bounds, identical final state whatever the render cadence. |
| REQ-LOOP-008 | The real time added per iteration is capped (default 0.25 s, configurable in `[one step, 1 s]`); the excess is dropped and reported; updates are never skipped below the cap (ADR-0017, ADR-0031). | Must | VALIDATED | Tests with an artificial long frame: number of updates, dropped time reported, no spiral of death. |
| REQ-LOOP-009 | Pause and resume cause no catch-up and no time shift; a time scale slows the simulation without changing the step and without losing rendered frames; interpolation is the default presentation, extrapolation is opt-in (ADR-0017). | Must | VALIDATED | Tests: pause then resume advances the simulation by zero steps; time scale 0.25 gives a quarter of the updates while render calls are unchanged. |
| REQ-LOOP-010 | An exception in an update or a render stops the loop in a failed state without swallowing it; a stop request is honored at a frame boundary, never inside a step, and is idempotent (ADR-0017). | Must | VALIDATED | Tests: exception propagation and failed state; stop mid-iteration finishes the step; double stop. |
| REQ-LOOP-011 | The update rate is an `int` in `[1, 1000]` Hz (default 60) and the step is `round(1e9 / rate)` nanoseconds in a `long` accumulator, the rounding remainder of scaled time being carried; the time scale is in `[0.1, 4.0]` (default 1.0, outside throws `IllegalArgumentException`); dropped lag is exposed as counters and an optional allocation-free listener (ADR-0031). | Must | VALIDATED | Controllable-clock tests: no drift over 10⁶ steps, range checks, counters and listener calls. |
| REQ-LOOP-012 | A measured elapsed time within 0.25 ms (configurable, `0` disables) of 1 to 4 steps is snapped to that multiple; the render call receives `alpha` and the unscaled real delta in seconds, which may advance presentation-only state (menus, UI) and never simulation state (ADR-0031). | Should | VALIDATED | Tests of snapping at and beyond the tolerance; render delta during pause and at time scale 0.25. |

## Runtime

Source: [ADR-0018](decisions/0018-runtime-thread-events-and-cache-thread-safety.md), [ADR-0019](decisions/0019-loading-resource-policy-and-memory.md), [ADR-0020](decisions/0020-no-reflection-factory-registry-and-capability-lookup.md), [ADR-0031](decisions/0031-runtime-defaults-loop-calibration-inbox-scenes-platform-lifecycle.md).

| ID | Requirement | Priority | Status | Expected verification |
|---|---|---|---|---|
| REQ-RT-001 | One runtime thread owns the loop, the update phase, the world, the caches and, by default, the render phase; every public type documents its thread; the engine starts no thread by itself; the platform runs the loop on the thread it requires. | Must | VALIDATED | Contract tests on a test platform; review of Javadoc thread tags. |
| REQ-RT-002 | Platform-originated events are posted from any thread to a FIFO inbox and delivered on the runtime thread at the start of an iteration, before the update steps; internal events stay synchronous in the update phase; listener registration during a dispatch takes effect after it. | Must | VALIDATED | Tests with a controllable clock and injected events: order, boundary, registration during dispatch. |
| REQ-RT-003 | Cache operations run only on the runtime thread; decoded data are immutable; worker threads never touch a cache. | Must | VALIDATED | Contract tests of the consuming modules; thread-confinement assertion tests. |
| REQ-RT-004 | Resources can be loaded synchronously; an opt-in asynchronous request returns a handle (pending, ready, failed, cancelled, progress) completed through the inbox, never blocking the update step; workers only decode. | Should | VALIDATED | Tests with a fake worker pool and a controllable clock: completion at the frame boundary, failure, cancellation. |
| REQ-RT-005 | Caches use explicit reference counting and explicit release, with no weak references or automatic eviction by default; reloading happens only for context-loss recovery and as an explicit frame-boundary reload. | Must | VALIDATED | Contract tests of release, scope release and reload at a frame boundary. |
| REQ-RT-006 | Per-step and per-frame paths allocate nothing in steady state; no finalizers or `Cleaner`; native memory is released explicitly. | Must | VALIDATED | JVM allocation tests in the headless suite; review. |
| REQ-RT-007 | Data-driven instantiation goes through an explicit registry instance of stable string ids and factories registered at startup; definition files name ids, never Java classes; an unknown id, a duplicate registration and an invalid parameter fail with a documented exception naming the id; no reflection, `ServiceLoader` or class scanning in the engine (ADR-0020). | Must | VALIDATED | Tests of registration, unknown id, duplicate id, typed parameters, two independent registries; build or review check that shared modules use no reflection. |
| REQ-RT-008 | Platform capabilities are looked up through a typed optional lookup on an explicit platform object; absence means unsupported; no class-name lookup (ADR-0020). | Must | VALIDATED | Contract tests with a test platform exposing and omitting a capability. |
| REQ-RT-009 | The inbox is bounded (default 1,024 events, configurable); posting never blocks beyond a short lock; an overflowing event is rejected, counted and reported once on the runtime thread; pause, resume, stop and time-scale requests are atomic request fields, never inbox entries (ADR-0031). | Must | VALIDATED | Tests: overflow counted and reported, control requests honored while the inbox is full. |
| REQ-RT-010 | Asynchronous handles change state only on the runtime thread; reading a value that is not ready throws `IllegalStateException`; a result arriving after cancellation is discarded and released; a load group reports the mean progress of its members; the platform worker pool defaults to 2 workers on desktop and 1 on Android, `0` meaning synchronous only (ADR-0031). | Should | VALIDATED | Tests with a fake worker pool: state changes at inbox delivery, late result after cancel, group progress. |

## Sprites, animations and sprite sheets

Source: [ADR-0003](decisions/0003-sprite-animation-and-sprite-sheet-contracts-in-graphics.md), [ADR-0026](decisions/0026-graphics-pixels-cache-transforms-animation-and-commands.md), [ADR-0033](decisions/0033-media-defaults-module-names-filters-graphics-data-audio.md). Features: [`features/sprite-sheet.md`](features/sprite-sheet.md), [`features/sprite.md`](features/sprite.md), [`features/animated-sprite.md`](features/animated-sprite.md). These requirements refine the broader REQ-SPR-001 and REQ-SPR-002, kept unchanged. Modifiable pixel data is a separately owned buffer: the cached shared source is never mutated, and a modified buffer becomes a new source. Sprite coordinates are in pixels of the logical frame (ADR-0002); the conversion from world meters is done by the camera view transform (ADR-0014, ADR-0029).

Note: the packet placeholders `REQ-GFX-SPR-NNN`, `REQ-GFX-ANI-NNN` and `REQ-GFX-SHT-NNN` are numbered `REQ-SPRITE-NNN`, `REQ-ANIM-NNN` and `REQ-SHEET-NNN` because `scripts/check-docs.py` recognizes identifiers made of one upper-case word and a number.

| ID | Requirement | Priority | Status | Expected verification |
|---|---|---|---|---|

# Requirements

**Status: VALIDATED — every row below is VALIDATED (owner delegation of 2026-11-23; details in ADR-0001 to ADR-0044) and `REQ-AGENT-001` to `REQ-AGENT-004` (validated by the owner on 2026-11-25, issue #910). A row added later starts PROPOSED until the owner validates it.**

Each requirement has a stable identifier. Agents must reference these identifiers in their plans, commits and reports. Identifiers are never reused: removed requirements are listed under [Retired identifiers](#retired-identifiers).

Priorities follow MoSCoW: **Must**, **Should**, **Could**. "Won't (for now)" items belong in `docs/vision.md` as non-goals. A Should or Could requirement is binding once its feature is scheduled: it is implemented as written, not reinterpreted.

The traceability matrix (requirement → decision → test) is in [`traceability.md`](traceability.md). The few questions still open are in [`open-questions.md`](open-questions.md).

## Game loop

Source: [ADR-0001](decisions/0001-technical-baseline-and-conventions.md) (principles), [ADR-0017](decisions/0017-fixed-step-game-loop.md), [ADR-0031](decisions/0031-runtime-defaults-loop-calibration-inbox-scenes-platform-lifecycle.md). The text of REQ-LOOP-004 to REQ-LOOP-006 is the ADR-0001 principle, unchanged; REQ-LOOP-007 to REQ-LOOP-012 make it precise.

| ID | Requirement | Priority | Status | Expected verification |
|---|---|---|---|---|
| REQ-LOOP-001 | The game loop has a contract independent of its implementation. | Must | VALIDATED | Contract tests. |
| REQ-LOOP-002 | Several loop implementations can be provided. | Must | VALIDATED | Tests with a controllable clock and scheduler. |
| REQ-LOOP-003 | Update and render are distinct concepts. | Should | VALIDATED | Execution order verified by test. |
| REQ-LOOP-004 | The default implementation is independent of machine power and frequency. | Must | VALIDATED | Same simulation and same final state for an identical simulated time. |
| REQ-LOOP-005 | The default loop combines frameskipping and extrapolation to adapt presentation to the available time. Frameskipping may drop a presentation, never arbitrary simulation computations. | Must | VALIDATED | Tests of cadence, render skipping and extrapolation. |
| REQ-LOOP-006 | An extrapolation greater than 1 must not reduce simulation accuracy; an extrapolated state is never reused as input of the next simulation step. | Must | VALIDATED | Tests showing the simulated state is always computed from the reference simulation time/scheme, without integrating the extrapolated state. |
| REQ-LOOP-007 | The default loop advances the simulation by a fixed step (default 60 Hz, configurable) from an abstract monotonic clock, using an accumulator and catch-up; the presentation factor `alpha = accumulator / step` is always in `[0, 1)` (ADR-0017). | Must | VALIDATED | Controllable-clock tests: exact number of updates for a given elapsed time, `alpha` bounds, identical final state whatever the render cadence. |
| REQ-LOOP-008 | The real time added per iteration is capped (default 0.25 s, configurable in `[one step, 1 s]`); the excess is dropped and reported; updates are never skipped below the cap (ADR-0017, ADR-0031). | Must | VALIDATED | Tests with an artificial long frame: number of updates, dropped time reported, no spiral of death. |
| REQ-LOOP-009 | Pause and resume cause no catch-up and no time shift; a time scale slows the simulation without changing the step and without losing rendered frames; interpolation is the default presentation, extrapolation is opt-in (ADR-0017). | Must | VALIDATED | Tests: pause then resume advances the simulation by zero steps; time scale 0.25 gives a quarter of the updates while render calls are unchanged. |
| REQ-LOOP-010 | An exception in an update or a render stops the loop in a failed state without swallowing it; a stop request is honored at a frame boundary, never inside a step, and is idempotent (ADR-0017). | Must | VALIDATED | Tests: exception propagation and failed state; stop mid-iteration finishes the step; double stop. |
| REQ-LOOP-011 | The update rate is an `int` in `[1, 1000]` Hz (default 60) and the step is `round(1e9 / rate)` nanoseconds in a `long` accumulator, the rounding remainder of scaled time being carried; the time scale is in `[0.1, 4.0]` (default 1.0, outside throws `IllegalArgumentException`); dropped lag is exposed as counters and an optional allocation-free listener (ADR-0031). | Must | VALIDATED | Controllable-clock tests: no drift over 10⁶ steps, range checks, counters and listener calls. |
| REQ-LOOP-012 | A measured elapsed time within 0.25 ms (configurable, `0` disables) of 1 to 4 steps is snapped to that multiple; the render call receives `alpha` and the unscaled real delta in seconds, which may advance presentation-only state (menus, UI) and never simulation state (ADR-0031). | Should | VALIDATED | Tests of snapping at and beyond the tolerance; render delta during pause and at time scale 0.25. |

## Sprites, animations and sprite sheets

Source: [ADR-0003](decisions/0003-sprite-animation-and-sprite-sheet-contracts-in-graphics.md), [ADR-0026](decisions/0026-graphics-pixels-cache-transforms-animation-and-commands.md), [ADR-0033](decisions/0033-media-defaults-module-names-filters-graphics-data-audio.md). Features: [`features/sprite-sheet.md`](features/sprite-sheet.md), [`features/sprite.md`](features/sprite.md), [`features/animated-sprite.md`](features/animated-sprite.md). These requirements refine the broader REQ-SPR-001 and REQ-SPR-002, kept unchanged. Modifiable pixel data is a separately owned buffer: the cached shared source is never mutated, and a modified buffer becomes a new source. ## Network and multiplayer

Source: [ADR-0038](decisions/0038-network-model-server-authority-snapshots-prediction.md) (model, modules) and [ADR-0039](decisions/0039-network-protocol-transport-sessions-and-defaults.md) (protocol, sessions, defaults). Features: [`features/network.md`](features/network.md) (module `network`), [`features/multiplayer.md`](features/multiplayer.md) (module `multiplayer`). Both modules are optional; their priority applies once network play is scheduled (roadmap Phase 5).

| ID | Requirement | Priority | Status | Expected verification |
|---|---|---|---|---|
| REQ-NET-001 | Module `network` provides client-server sessions (`NetworkServer`, `NetworkClient`) on `core` only, as shared code for desktop and Android; a host runs a server and a local client in one process; everything runs on the runtime thread through a session `update` called once per step, with non-blocking transports and no thread started (ADR-0038, ADR-0039). | Should | VALIDATED | Dependency check (REQ-CORE-005); headless tests over the loopback transport; thread-confinement tests. |
| REQ-NET-002 | Transports: UDP through a non-blocking `DatagramChannel` using API 21 calls only, an in-process loopback, and a wrapper simulating latency, jitter, loss, duplication and reordering from a seed; IPv4 and IPv6 literals; default port 19880 (`[1024, 65535]`); datagram payload at most 1,200 bytes by default (`[512, 1472]`) (ADR-0039). | Should | VALIDATED | Transport contract suite of the `network` test JAR (ADR-0045) on loopback and on UDP bound to the local address; seeded-conditions determinism test. |
| REQ-NET-003 | Every packet has a 21-byte header (CRC32 salted with the protocol id and version, type, 64-bit session token, `uint16` sequence, ack and 32 ack bits); a corrupted, foreign, malformed or unmatched packet is dropped and counted, never thrown into game code (ADR-0039). | Should | VALIDATED | Unit tests: checksum with another id or version, wrap-around, ack bits, each malformed case. |
| REQ-NET-004 | Two channels: unreliable-sequenced (newest wins) and reliable-ordered (delivered once and in order; resent at most every 0.1 s until acknowledged; 256 in flight; queue of 1,024 then `OVERFLOW`); messages up to 64 KiB and snapshots are fragmented; a keepalive is sent after 0.1 s without traffic (ADR-0039). | Should | VALIDATED | Unit tests of ordering, resend interval, window, overflow, fragmentation; integration under simulated loss and reordering. |
| REQ-NET-005 | A client joins by IP address and port with a player name; the padded connect request (resent every 0.5 s, given up after 10 s) is checked in the order protocol, game id and version, content hash, joinable, capacity (default 16, `[1, 64]`), name (1 to 24 characters, no control characters, unique ignoring case), authenticator (default accept); a refusal gives the first failing reason (ADR-0039). | Should | VALIDATED | Unit tests of each check and its order; integration join over loopback and UDP. |
| REQ-NET-006 | A connection times out after 10 s without packets (`[1, 60]` s); a leave sends `DISCONNECT` three times with a reason (`QUIT`, `KICKED`, `SERVER_SHUTDOWN`, `TIMEOUT`, `OVERFLOW`, `PROTOCOL_ERROR`); connection state changes reach a listener on the runtime thread (ADR-0039). | Should | VALIDATED | Controllable-time tests of timeout, keepalive and graceful leave. |
| REQ-NET-007 | Every peer holds the same player list ordered by id: id (`int` from 1, never reused in a session, `0` is the server), name, host flag, round trip broadcast once per second, properties; joined, left (with reason) and changed events reach every peer (ADR-0039). | Should | VALIDATED | Integration: identical lists on all peers after joins, leaves and renames under simulated conditions. |
| REQ-NET-008 | Player properties (at most 16, key `[a-z][a-z0-9_-]*` up to 32 characters, value up to 128) are set by the server or requested by the player and accepted by a server validator (default accept), and replicated reliably to everyone (ADR-0039). | Should | VALIDATED | Unit tests of limits and validation; integration of replication. |
| REQ-NET-009 | The server can kick a player with a text, open or close joining, set its name and stop with `SERVER_SHUTDOWN`; a player can request a name change checked like a new name (ADR-0039). | Should | VALIDATED | Integration tests of each action and of the events it causes. |
| REQ-NET-010 | Chat: texts of 1 to 256 characters to everyone or to one player, sent to the server, passed to a filter (default unchanged; may change or drop) and relayed; at most a burst of 5 then 1 per second per player, excess dropped with a notice to the sender; server messages have sender `0` (ADR-0039). | Should | VALIDATED | Unit tests of filter and rate limit; integration of delivery to targets. |
| REQ-NET-011 | Game messages: types registered by id `namespace:name` with a codec and a delivery (`RELIABLE` or `UNRELIABLE`), in the same order on both sides and included in the content hash (32-bit FNV-1a over the message types and an extra hash given by the game or `multiplayer`); client to server, server to one, everyone or everyone but one; listeners receive the sender id on the runtime thread; at most 64 KiB reliable and one datagram unreliable (ADR-0039). | Should | VALIDATED | Unit tests of registration, size limits and routing; integration under simulated conditions. |
| REQ-NET-012 | Per-connection statistics are readable at any time without allocation: smoothed round trip (factor 0.1), loss over the last 64 packets, bytes per second each way, dropped packets by cause, resent messages, connection attempts (ADR-0039). | Should | VALIDATED | Unit tests with a controllable time and the conditions wrapper; allocation test. |
| REQ-NET-013 | A server answers padded information requests (name, game id and version, protocol version, players, maximum, joinable); LAN discovery broadcasts a request on IPv4 and collects answers for 1 s by default; on Android the hosting device holds the multicast lock provided by `platform-android` (ADR-0039). | Could | VALIDATED | Integration test of the information query over loopback; platform tests of broadcast on desktop and Android. |
| REQ-NET-014 | Security baseline: random 64-bit session tokens from `SecureRandom`, token and address checks, padded requests (no amplification), one pending connection per address, bounds checks on every read; and extension points so that encryption and authentication can be added by a new protocol version without changing the session API: protocol version in the checksum, opaque authentication data (at most 512 bytes) with an `Authenticator`, a `PacketProtection` stage (identity in version 1) (ADR-0039). | Should | VALIDATED | Unit tests of token and address checks, padding and limits; review of the extension points. |
| REQ-NET-015 | Wire values are written and read by `NetWriter` and `NetReader` over preallocated arrays, big-endian: integers, variable-length integers, `float` and `double` as exact IEEE bits, UTF-8 strings with a checked maximum; no reflection or Java serialization (ADR-0020, ADR-0039). | Should | VALIDATED | Round-trip unit tests of every type and limit. |
| REQ-NET-016 | In steady state, sending and receiving unreliable traffic allocates nothing on the engine side; JDK allocations of the socket API are measured and recorded; joining, reliable messages, chat and events may allocate (ADR-0039, REQ-RT-006). | Should | VALIDATED | JVM allocation test of the per-step paths over loopback and UDP. |
| REQ-NET-017 | The module is testable headless: every behavior runs over the loopback and conditioned transports with a controllable monotonic time source (default `System.nanoTime`); no wall-clock dates are used (ADR-0039). | Should | VALIDATED | The integration tests of this table run in the headless suite. |
| REQ-MP-004 | Server authority: only the server creates and removes replicated objects and decides outcomes; clients send per-tick input frames and commands (reliable game messages); module `multiplayer` depends on `network`, `ecs`, `traits`, `input-api` and `core`, not on `runtime` or a platform, and nothing depends on it; the game calls the server or client world's `update` once per step instead of `world.update` (ADR-0038). | Should | VALIDATED | Dependency check; integration test of a host and a client over loopback. |
| REQ-MP-005 | A replication schema registers, in the same order on both sides, replicated object types (registry ids, one factory per side), replicated trait types with a codec (write, read, optional interpolate; at most 64), predicted types and the input action layout; its 32-bit hash, combined by `network` with the game message types, is the content hash checked when a client joins (ADR-0038, ADR-0039). | Should | VALIDATED | Unit tests: hash changes with any registration change; join refused with `CONTENT_MISMATCH`. |
| REQ-MP-006 | Every snapshot interval (default 3 ticks, `[1, 60]`), the server sends each client a snapshot of the relevant replicated objects (network ids `int` from 1 never reused, type, owner, traits) delta-compressed by byte comparison against the client's last acknowledged snapshot, complete when no baseline is kept (history 64); object existence is part of the snapshot; a snapshot above the size limit (default 64 fragments, at most 255) is not sent and is reported (ADR-0038). | Should | VALIDATED | Unit tests of delta encoding and decoding, removal by absence, baseline fallback, size limit. |
| REQ-MP-007 | Convergence: under any loss, duplication, reordering and delay, once a client applies a snapshot of tick T, the replicated traits of its proxies equal the server's values of tick T exactly with the standard codecs, and no replicated object exists on one side only (ADR-0038). | Should | VALIDATED | Convergence suite over the conditioned transport with fixed seeds (`features/multiplayer.md`). |
| REQ-MP-008 | On a client, replicated objects are proxies carrying `NetProxy`, excluded from simulation systems; they are shown at the newest server tick minus the interpolation delay (default 2 snapshot intervals, `[0, 1]` s), interpolated by their codecs or holding the older value, and held without a newer snapshot; game code creating or removing replicated objects or removing their replicated traits on a client fails at the flush with `IllegalStateException` (ADR-0038). | Should | VALIDATED | Unit tests of interpolation, hold and the structural rule; integration with the conditions wrapper. |
| REQ-MP-009 | Input frames hold, per tick, 3 bits per digital action and a 16-bit value per analog action; the client simulates with the decoded frame it sends and repeats up to 32 unacknowledged frames per packet; the server buffers 64 ticks per player, applies the frame of tick T at T, repeats held states without edges when a frame is missing, merges the edges of a late frame into the next applied one, and exposes each player's `InputState` driven by frames (ADR-0035, ADR-0038). | Should | VALIDATED | Unit tests of encoding, quantization, missing and late frames (a press is never lost); integration under loss. |
| REQ-MP-010 | Tick alignment: the server reports each client's input lead with each snapshot; the client targets 2 ticks (`[0, 10]`), runs 2 ticks in one update below 1 and 0 ticks above target plus 3, at most once every 10 ticks, and jumps when more than 60 ticks off, clearing its prediction history (ADR-0038). | Should | VALIDATED | Unit tests of each pacing decision; integration with latency changes. |
| REQ-MP-011 | Prediction, opt-in per object type and only for objects owned by the local player: the client keeps 64 ticks of frames and encoded predicted state; on a snapshot of tick T it compares bytes, and on a difference writes the server state and replays ticks T+1 to now with `isReplaying()` true; beyond the history it takes the server state without replay; corrections and snaps are counted (ADR-0038). | Should | VALIDATED | Unit tests of comparison, replay and snap; integration: a predicted avatar ends at the server's position under latency and loss. |
| REQ-MP-012 | An optional relevance filter decides per player and object whether the object is sent; default everything; an irrelevant object disappears from that client and reappears when relevant again (ADR-0038). | Could | VALIDATED | Unit and integration tests with a distance-based filter. |
| REQ-MP-013 | Standard codecs exist for `Transformable` (position interpolated linearly), `Movable`, `Gravity`, `Jumpable`, `Collidable` and `Lifetime`, writing every `double` exactly (ADR-0038). | Should | VALIDATED | Codec contract suite of the `multiplayer` test JAR (ADR-0045) run on each standard codec. |
| REQ-MP-014 | A host runs the server world and an ordinary client world connected through the loopback transport in one process; a dedicated server runs a server world on the headless platform (ADR-0038). | Should | VALIDATED | Headless example of a host with one remote client; dedicated-server integration test. |

## Context

Batch 1 of the feature page is "IDs, world, create/remove, liveness, explicit flush". The rules are fixed: a packed `long` ID with the generation in the high 32 bits, the index in the low 32 bits and a first generation of 1 (ADR-0030, decision 1); a created object pending until the flush, commands in recorded order, a creation and a removal of the same step both applied, an explicit flush outside the loop (decision 2); a capacity of 1,024 objects by default, configurable and grown by `reserve`, doubling at the flush and never shrinking (ADR-0034, ADR-0030 decision 4); a liveness check that never throws and accessors that fail fast with a defined error (ADR-0011, decision 2). The documents leave open the Java signatures, the generation range and what happens when it is exhausted, the order in which free indices are reused, the errors, a removal recorded twice, where the capacity grows when more objects are created than it holds, and the size of the command log.

## Decision

1. **Types.** `World`, a final class, and `WorldConfig`, a record in the style of `LoopConfig`, both in `com.b3dgs.lionengine.ecs`. `new World()` uses `WorldConfig.DEFAULT`; `new World(config)` refuses `null` with `IllegalArgumentException`. Public members of the batch: `World.NO_OBJECT` (`0L`), `create()`, `remove(long)`, `isAlive(long)`, `flush()`, `reserve(int)`, `getObjectCount()` (alive objects as of the last flush) and `getObjectCapacity()`; `WorldConfig(int objectCapacity)` with `DEFAULT_OBJECT_CAPACITY` (1,024), `MAX_OBJECT_CAPACITY` (2<sup>30</sup>) and `DEFAULT`. The trait capacity, the grid cell size and the random seed of the feature page join `WorldConfig` with the batches that use them (no backward compatibility is kept, `AGENTS.md`). The index table and the command log are package-private (`ObjectTable`, `StructuralCommands`).
2. **Generation range.** Generations go from 1 to 2<sup>31</sup> − 1, so every ID is positive: `0` and every negative value never name an object, and comparing IDs as signed `long` values orders them by generation then index, which the ascending ID copy of batch 3 relies on. An index whose object is removed at generation 2<sup>31</sup> − 1 is **retired**: never reused, so no ID is ever issued twice by a world. At one removal per step on the same index at 60 Hz, retirement takes more than a year of play.
3. **Index reuse.** The flush releases the index of a removed object with the next generation and puts it at the back of a free queue; `create` takes the oldest free index first, then a new index. Oldest first spreads the generations over the indices and keeps a just-freed index out of use for as long as possible; both orders are deterministic for the same operation sequence (`REQ-DET-001`). A removal frees its index only at the flush: a creation recorded before that flush never reuses it.
4. **Errors.** `remove(id)` refuses a stale ID and an ID that never named an object of the world (`NO_OBJECT` included) with `IllegalArgumentException`. The accessors of the next batches use the package-private `checkAlive(id)`: `IllegalStateException` for a pending object (a call in the wrong state, the object exists), `IllegalArgumentException` for a stale or never-valid ID. `isAlive` never throws. Messages name the ID; they are built on the failure path only.
5. **Removal recorded twice.** `remove` accepts a pending or alive object, also when its removal is already recorded; at the flush, a removal whose object is no longer alive (removed by an earlier command of the same flush) changes nothing. Two systems may therefore remove the same object in one step (a bullet hitting two enemies) without coordinating; only the first removal is effective, and only effective changes will fire events (batch 4, `REQ-ECS-012`).
6. **Creating beyond the capacity.** `create` never allocates: an index beyond the table is issued as pending with the first generation, and the flush first doubles the table until every issued index fits, then applies the commands; `reserve(n)` grows it to `n` at once, outside the steps. This is the growth "at the flush" of ADR-0030. The table holds at most 2<sup>30</sup> indices: `create` beyond it throws `IllegalStateException`.
7. **Command log.** Parallel primitive arrays of a command kind and an object ID, starting at the object capacity, doubling when a step records more commands (a warm-up cost like the table's), never shrinking, at most 2<sup>30</sup> commands per flush (`IllegalStateException` beyond). The trait commands of batch 2 are new kinds of the same log, so creations, trait changes and removals keep one recorded order.
8. **Seams for the next batches.** The flush is where batch 2 applies trait commands and batch 4 fires its events; re-entrancy (a listener recording commands or calling `flush` during a flush) is decided with the listeners of batch 4, since no code of batch 1 runs during a flush. `World.update(stepSeconds)` comes with the systems of batch 4, the random source with batch 5.
9. **Threads and allocation.** A world is not thread-safe and is used on the runtime thread only (ADR-0018); no check is made, as for the other per-step types. Measured by `WorldAllocationTest` with the per-thread allocation counter: 1,000 steps of 1,000 removals, 1,000 creations and one flush (2 million commands and 1,000 flushes) allocate less than the 1 KiB tolerance of the counter, after a warm-up that grows the default table once to 2,048 (removed objects free their index only at the flush, so such a step holds 2,000 indices). Wall-clock time is the benchmark of batch 6 (`REQ-ECS-009`).

## Options considered

- Generation range: 1 to 2<sup>31</sup> − 1 with retirement (chosen; positive IDs, no ID ever repeats) vs the full unsigned 32 bits (negative IDs, signed order no longer by generation) vs wrapping back to 1 (an old ID can come back to life after 2<sup>31</sup> reuses).
- Reuse order: oldest free index first (chosen) vs last freed first (better cache locality in the index table, but the same few indices take every generation, and a just-removed object's index is reused at once, which makes a stale-ID bug harder to see).
- Removal recorded twice: ignored at the flush (chosen) vs refused at the call (needs a "removal pending" flag per object, and forces game systems to coordinate).
- Growth when creating beyond the capacity: at the flush, pending indices issued without storage (chosen; what ADR-0030 states, and `create` stays allocation-free) vs growing at `create` (simpler, but allocates in the middle of a step).
- Pending-object error: `IllegalStateException` (chosen; the conventions' wrong-state exception) vs `IllegalArgumentException` like a stale ID (hides that the object exists and will be alive after the flush).

## Consequences

- Positive consequences: IDs that are never reissued and whose order is meaningful; no allocation on the create, remove and flush paths once the capacities fit the busiest step; games remove objects from several systems without coordinating.
- Costs / constraints: a step that removes and creates N objects holds 2N indices; an index can retire (after more than two billion reuses); the capacity can only be lowered by creating a new world.
- Impact on modules and APIs: `ecs` gains its first public types; `examples` depends on `ecs` (`ObjectLifecycleExample`); the Android device tests gain `EcsTest`.
- Impact on tests and documentation: unit tests of packing, reuse, retirement, pending and stale IDs, capacities and growth, two independent worlds, a regression set of the flush order and an allocation test; `features/ecs.md` (State), `features/README.md`, `traceability.md`, `contracts.md`, `interfaces.md`, `api-index.md`, `engine-features.md`, `roadmap.md`, `agent-workflow.md`.

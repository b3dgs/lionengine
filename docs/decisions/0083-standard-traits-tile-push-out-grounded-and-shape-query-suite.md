## Context

Batch 4 of [`../features/standard-traits.md`](../features/standard-traits.md) delivers the tile collision of the standard traits. The rules are fixed: tiles block through a basic axis-separated push-out that sets `grounded` from a contact below, in the first tile-collision batch, because `grounded` needs it; triggers never block; object versus object stays detection only; no swept detection, the displacement per step staying under half of the smallest collider (ADR-0030, decisions 6 and 7; `REQ-STD-010`); `grounded` is a field of `Jumpable`, set by the collision system and also settable by the game, with the defaults of `REQ-STD-004` (ADR-0030, decision 7; ADR-0034); `tilemap` implements the `physics` shape-query contract with a world placement in meters, default 1 m per tile, and never depends on `ecs` (ADR-0028, decision 1; `REQ-MAP-008`); `ShapeQuery` is `int query(Box area, Box[] results)` with caller buffers, strict overlap, no allocation, its implementation and contract suite left to the tile-collision batch (ADR-0082, decision 4); the `Collision` system runs at slot 4000 (ADR-0034); each standard system takes excluded trait types (`REQ-STD-011`).

The documents leave open the order between this batch and its two dependencies (`Jumpable`, standard-traits batch 5, and the tile map's `ShapeQuery`, tile-map batch 5 after batches 1 to 4, no `tilemap` code existing yet), where the push-out runs and how it receives the query, the axis order, whether the velocity is zeroed, the contact rule of `grounded` while the overlap is strict, whether a tile contact reports an event, which objects are pushed, a tile layer, the result buffer, the contract suite, and the names and checks of the `Jumpable` fields.

## Decision

1. **Dependencies (owner answer).** The batch is done against `ShapeQuery` only, tested with the reference `BoxListQuery` and a grid stand-in of the tile map; the tile map's implementation stays tile-map batch 5. `Jumpable` is brought forward as a complete data trait (impulse, `grounded`, coyote time, jump buffer, cut factor and its switch, every default from `REQ-STD-004`); the `Jump` system, its timers and the jump requests stay standard-traits batch 5.
2. **Placement (owner answer).** The push-out runs inside `CollisionSystem` at slot 4000, first in its step, before the object detection, so the pairs are those of the pushed positions. Two constructors add it: `(world, transformables, collidables, movables, jumpables, tiles)` and `(world, transformables, collidables, movables, jumpables, cellSize, excluded)` (seven parameters at most); `setShapeQuery(ShapeQuery)` replaces the query for a map change, from the next step, `null` for none; `getShapeQuery()` and `getTileQuery()` read them. One query per world: a game with several maps gives a query of its own over them. The three constructors of batch 3 are unchanged and have no push-out (the tile methods are then an `IllegalStateException`).
3. **Algorithm (owner answer).** For each pushed object, its displacement of the step measured from its previous position (captured at the step start): an X pass with the box at `(x, previousY)`, moving right put at the left of the leftmost overlapping shape, moving left at the right of the rightmost one; then a Y pass with the box at the resolved X and `y`, moving down put on the highest overlapping shape, moving up under the lowest one; an axis without displacement has no pass. A velocity component pointing into a shape that stopped the object is set to `0`, one pointing away is kept. The object's `Jumpable`, if any, is grounded if and only if the Y pass pushed it up; with no query the flags are not written. No tolerance: a resting object is grounded at each step only while something (a gravity) moves it into the floor; one resting without displacement is not. No event reports a tile contact.
4. **Pushed objects (owner answer).** Every non-trigger object having `Transformable`, `Collidable` and `Movable` and none of the excluded types (a second query of the system, exposed by `getTileQuery()`); an object without `Movable` has no displacement and is not pushed; triggers are never pushed and their flag is not written. No tile layer or mask: every pushed object collides with the tiles whatever its layer and mask.
5. **Buffer and suite (owner answer).** The result buffer of the queries starts empty and grows to `max(count, 2 * length)` boxes when a query returns more shapes than it holds, then the query is repeated: a warm-up cost, no allocation in steady state. `ShapeQueryContract`, an abstract suite in the `physics` test JAR, is bound by `BoxListQuery` now and by the tile map later; its shapes are tiles of 1 m on a grid at the origin, columns and rows in `[0, 8)`, so a map of 1 m tiles at the origin represents them. It checks the strict overlap (touching not found), the written boxes, the count beyond the buffer, the untouched remainder, the `null` arguments, an order depending only on the content and the area, nothing kept, and no allocation (JVM allocation counter, 1 KiB over 10,000 queries).
6. **Exact contact.** A pushed box ends exactly touching the shape: the position is computed from the shape bound, the half size and the offset, then moved by the last ulps (`Math.nextUp`, and `Math.nextAfter` toward negative infinity since `Math.nextDown` needs Android API 24) until the box bound, computed as `Box` computes it, is not beyond the shape bound. A resting box therefore never overlaps the floor it rests on, and an object walking on a floor of several tiles does not catch on their seams in the next X pass.
7. **`Jumpable` data.** Private fields `impulse`, `coyoteTime`, `jumpBuffer`, `cutFactor` (`double`) and `variableHeight`, `grounded` (`boolean`), the parameter names of ADR-0032 for the registry id `lionengine:jumpable` (the switch named `variableHeight`); accessors `getImpulse`, `setImpulse`, `isGrounded`, `setGrounded`, `getCoyoteTime`, `setCoyoteTime`, `getJumpBuffer`, `setJumpBuffer`, `getCutFactor`, `setCutFactor`, `isVariableHeight`, `setVariableHeight`, a public `TYPE` and the constants `DEFAULT_COYOTE_TIME`, `DEFAULT_JUMP_BUFFER` (`0.1` s each) and `DEFAULT_CUT_FACTOR` (`0.5`). Reset state: impulse `0`, not grounded, the default times and factor, no variable height. A negative or non-finite impulse or time, and a cut factor outside `[0, 1]` or `NaN`, are an `IllegalArgumentException` (a factor above 1 would raise the jump on a release). No factory for `lionengine:jumpable` yet (`OQ-178`).
8. **Bytes per instance.** Measured by `TraitMemoryTest`: 48 bytes per `Jumpable` on the desktop JVM (64-bit HotSpot, compressed class pointers), written in its Javadoc and asserted as an upper bound.
9. **Allocation and benchmark.** `TileCollisionAllocationTest` asserts no allocation over 1,000 steps of the 1,000 objects of the tile scene with the 1 KiB tolerance, after a warm-up. The tile scene (`TileBenchmarkWorld`: squares of 0.5 m walking at 2 m/s and hopping at 5 m/s when grounded under a gravity of -9.81 m/s² limited to 10 m/s, in an arena of 1 m tiles of 4 m² per object with a floor, two walls and full-width platforms every four rows, the capture, a hop system at 1500, `Gravity`, `Movement` and `Collision` with the tiles) is measured with `StepHarness` at 1,000 and 10,000 objects by `StepBenchmarkTest`, in the collision section of its report, without a budget (no document states one).

## Options considered

- Dependencies: `Jumpable` data now (chosen: the documented field, every default stated) vs `Jumpable` with `grounded` only (a partial trait completed later) vs a separate flag trait (diverges from the documented field) vs reordering batches 4 and 5 (`Jump` without the ground it needs).
- Placement: inside `CollisionSystem` (chosen: the feature table puts the push-out in the `Collision` row; the pairs see the pushed positions) vs a separate system at slot 4000 registered first (a tie rule to remember) vs a separate system at an undocumented slot.
- Algorithm: X then Y from the previous position (chosen: no seam snag, a falling object reaching a wall corner lands on it, no value to choose) vs the smaller penetration first (snags on the seams of a floor) vs a contact probe for `grounded` (a tolerance no document states).
- Objects: non-trigger with `Movable`, no tile layer (chosen) vs a tile layer tested against the masks (a layer value to choose) vs pushing objects without `Movable` by the smaller penetration (no displacement to oppose).

## Consequences

- Positive consequences: platform games can stand on and walk into solid tiles and read `grounded` from the standard traits; the tile map has a contract suite to bind; the push-out allocates nothing and depends only on each object and the shapes (`REQ-DET-001`).
- Costs / constraints: a world using the push-out registers `Movable` and `Jumpable`; one shape query per world; an object resting without gravity is not grounded; displacement per step under half of the smallest box, the object's and the tile's; the push-out costs one or two shape queries per moving object and step.
- Impact on modules and APIs: `traits` gains `Jumpable`, the two constructors and the tile methods of `CollisionSystem`, and the package-private `TilePushOut`; `physics` gains `ShapeQueryContract` in its test JAR (the `traits` tests depend on it); `examples` gains `LandingExample`, `Landing` and `Ground`; the Android verification extends `PhysicsTest`.
- Impact on tests and documentation: `features/standard-traits.md`, `features/README.md`, `contracts.md`, `interfaces.md`, `api-index.md`, `engine-features.md`, `roadmap.md`, `agent-workflow.md`, `traceability.md`, `testing.md`, `android-compatibility.md`, `glossary.md`.

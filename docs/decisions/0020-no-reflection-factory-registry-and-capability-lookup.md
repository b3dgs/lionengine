# ADR-0020 — No reflection: factory registry for data-driven objects and typed capability lookup

- Status: ACCEPTED
- Date: 2026-11-22
- Decision makers: project owner
- Related requirements: `REQ-RT-007`, `REQ-RT-008`, `REQ-TECH-006`, `REQ-TECH-007`, `REQ-ECS-010`
- Open questions resolved: `OQ-034`, `OQ-152` (follow-up: `OQ-154`)
- Supersedes / superseded by: none; completes [ADR-0011](0011-ecs-dynamic-objects-traits-and-standard-traits.md) (which stays unchanged)

Source: owner decision "option A, so no reflection" on issue #877.

## Context

The previous engine configured objects dynamically from XML by supplying a class name and instantiating it by reflection. Under R8 minification classes and constructors reachable only by name are renamed or removed, so every type needs keep rules; startup is slower; errors surface as `ClassNotFoundException`; and a data file naming any class can instantiate unintended ones. `ServiceLoader` is reflective as well. [ADR-0011](0011-ecs-dynamic-objects-traits-and-standard-traits.md) already forbids reflection in update paths. Platform capabilities (`OQ-034`) also needed a lookup mechanism.

## Decision

- **No reflection** in the engine: no class lookup by name, no reflective instantiation, no `ServiceLoader`, no class scanning, no runtime bytecode generation. This applies to every shared module; platform modules avoid it unless a platform API requires it; test code is not restricted.
- **Data-driven instantiation uses an explicit registry of factories.** The game registers, at startup and before any loading, a stable string id per type together with a factory (for example a constructor reference). A definition file names the **id**, never a Java class, and gives parameters as attributes. Each factory receives a typed configuration and reads its parameters by name and type, with defaults and clear errors.
- The registry is an **instance** passed explicitly (no singleton, no global state); several registries can coexist. A mod or plugin registers further factories at startup.
- Defined errors: an unknown id, a duplicate registration and an invalid parameter each fail with a documented exception naming the id (and the parameter) (`REQ-RT-007`).
- **Platform capabilities** use a **typed optional lookup** on an explicit platform object: the platform returns an optional typed contract defined in the relevant `*-api` module; absence means unsupported; limits are fields of the returned contract; negotiated features use best effort and the effective result (ADR-0006). Modules are wired explicitly by the application (`REQ-RT-008`).
- Generating the registry at build time with an annotation processor (no hand-written registration) is a possible later convenience, not part of this decision (`OQ-154`).

## Options considered

- A: explicit registry (retained): simple, R8-safe, fast, clear errors, no instantiation of arbitrary classes. Cost: one registration line per type.
- B: registry generated by an annotation processor: removes the lines, adds a processor and a dependency to review (`OQ-148`, Android compatibility). Deferred.
- C: reflection with keep rules: closest to the old engine, fragile under R8, unsafe for mods. Rejected.

## Consequences

- Positive consequences: works unchanged under R8 and DEX; fast, predictable startup; errors named by id; data files cannot instantiate unintended classes; typed, discoverable capabilities.
- Costs / constraints: every instantiable type must be registered; definition files refer to ids, so ids must stay stable and unique; the old XML files that name classes need migration (no backward compatibility is required, `AGENTS.md`).
- Impact on modules and APIs: the registry contract and typed configuration live in the module hosting definitions (to place with `OQ-146`, `OQ-126`); platform modules expose capability contracts in the `*-api` modules.
- Impact on tests and documentation: tests of registration, unknown id, duplicate id, typed parameters and independence of two registries; `conventions.md` and `overview.md` updated.

## Validation

Decision confirmed by the project owner on 2026-11-22 (issue #877). The owner chose option A for `OQ-152`; the typed capability lookup of `OQ-034` was proposed with it and is read as confirmed by "no reflection"; the owner can reverse it on issue #877.

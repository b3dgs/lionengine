## Context

Batch 4 of the feature page is "events and system ordering". The rules are fixed: object created and destroyed and trait added and removed events, delivered synchronously during the flush (ADR-0011 decision 7); listeners as plain interfaces with primitive arguments, registered on the world, on the runtime thread: `(long objectId)` and `(long objectId, int traitTypeId)` (ADR-0034); listener rules of ADR-0018 (runtime thread only, registration and removal during a dispatch take effect at the end of that dispatch, no allocation per event, a listener exception fails fast); systems ordered by an `int` slot, lower first, ties by registration order, no dependency graph, an enabled flag applied at the next step, `world.update(step)` with the constant step in seconds, one flush per step at the end after all systems and before rendering, an exception propagating and leaving the world undefined (ADR-0030 decisions 2 and 5, `REQ-LOOP-010`); the standard slots `Jump` 1000, `Gravity` 2000, `Movement` 3000, `Collision` 4000, `Lifetime` 5000 and the recommended game ranges (ADR-0034); the canonical name `GameSystem` (ADR-0037); `XxxListener` with `onYyy` methods (`conventions.md`); the package-private change hook left by ADR-0075 and ADR-0076. The documents leave open the signatures, the listener and system collections and their growth, duplicate registrations, the removal of systems, what a listener changing the world during the flush does, what happens to commands recorded by listeners, what `update` does with an invalid step, with a registration during the update and with a flush requested by a system, how "the world is undefined" shows, and whether `update` reports the step count.

## Decision

1. **Listener types.** Two public interfaces in `ecs`: `ObjectListener` (`onCreated(long objectId)`, `onDestroyed(long objectId)`) and `TraitListener` (`onTraitAdded(long objectId, int traitTypeId)`, `onTraitRemoved(long objectId, int traitTypeId)`). Each method does nothing by default, so a game overrides only the events it needs (a listener of explosions implements `onDestroyed` only). One trait listener receives every trait type and compares the type ID of `TraitStorage.getTypeId()`: this is the "per trait type" of `REQ-ECS-007` with the arguments of ADR-0034; a per-storage registration can be added later without breaking a caller. They replace the package-private `ChangeHook`, which is deleted: the world delivers the same calls, at the same points, to the registered listeners.
2. **Registration.** `World.addObjectListener`, `removeObjectListener`, `addTraitListener`, `removeTraitListener`. Listeners are called in registration order. `null`, a listener registered twice in a world, and the removal of a listener that is not registered are an `IllegalArgumentException`. The same object may be registered as object and as trait listener, and in several worlds. Registration is allowed at any time, also from a listener during the flush.
3. **Collections and registration during a delivery.** Each list is an array replaced at every registration and removal (copy on write); a delivery iterates the array current at its start. A listener added during a delivery receives the events from the next one; a listener removed during a delivery still receives the current event, as it was in the array, and nothing after it: the "end of that dispatch" of ADR-0018, one dispatch being the delivery of one event. Registrations allocate one array, outside the steady paths; a delivery allocates nothing.
4. **Event content and state.** As the hook of ADR-0075 and ADR-0076: effective changes only, in flush order; a replacement as removed then added; an addition then a removal in one step both fire; an object removal fires its trait removals by ascending type ID, then its destruction. During an addition the trait is attached and the queries list the object; during a removal the trait is still attached and readable and the queries still list the object, the instance is reset after the last listener; during a destruction the ID is already stale (`isAlive` is `false`).
5. **A listener must not change the world.** During the flush, every structural change is refused with `IllegalStateException`: `create`, `remove`, `TraitStorage.add` and `remove`, `flush`, `update`, `register`, `createQuery`, `World.reserve`, `TraitStorage.reserve`, `addSystem` and `removeSystem`. A listener may read the world (liveness, traits, queries), change the data inside traits, register and remove listeners and enable or disable systems. Commands are therefore never recorded by listeners: a listener that needs a structural change keeps the ID in its own buffer and a system records the change in the next step. Recording them for the next flush was rejected for this batch: the staged trait instances and the free-index queue are reset at the end of the flush, so accepting commands during it needs a second log and new ordering rules; refusing is fail-fast, and accepting later is a compatible relaxation. A refusal not caught by the listener propagates like any listener exception (decision 9).
6. **System contract.** `GameSystem`, a public interface with one abstract method, `void update(double stepSeconds)`, so a lambda is a system. The system gets the world and its queries at construction; the world is not passed at each step.
7. **System registration.** `World.addSystem(GameSystem system, int slot)`: any `int` is a slot; the system is inserted after every system of a lower or equal slot, so equal slots run in registration order; it starts enabled. `removeSystem(system)` keeps the order of the others; a system registered again goes after its ties. `setSystemEnabled(system, enabled)` and `isSystemEnabled(system)`, which returns the flag the next update applies; `getSystemCount()`. `null`, a system registered twice in a world, and an unknown system are an `IllegalArgumentException`; the same system may be registered in several worlds. Parallel arrays (system, slot, requested flag, applied flag), 8 long at creation, doubling when full, never shrinking; the lookup by identity is linear, outside the steady paths except `setSystemEnabled`, which allocates nothing. The standard slot values are documented on `GameSystem` and defined as constants by `traits` with the standard systems (`features/standard-traits.md`), not by `ecs`.
8. **The update.** `World.update(double stepSeconds)` is one step: it copies the requested enabled flags to the applied ones, runs each applied system in order with the step, then flushes once. A flag changed during the step (by a system or a listener) or between two steps applies at the next update. Commands recorded before the update (inbox events, setup) and by the systems apply in recorded order at that flush, so changes are visible from the next step and the state read between two updates (rendering) is stable (`REQ-ECS-010`). A step that is zero, negative, infinite or NaN is an `IllegalArgumentException` and nothing runs (ADR-0017: the step is the positive constant of the loop). During the update, `flush`, `update`, `addSystem` and `removeSystem` are an `IllegalStateException`, which enforces one flush per step; recording commands, `register`, `createQuery` and `reserve` are allowed. `update` returns nothing and the world counts no steps: the loop owns the step count (ADR-0017) and the scene passes it if a system needs it. The explicit `flush()` stays allowed between two updates and outside the loop.
9. **Failure.** An exception thrown by a system or a listener propagates out of `update` or `flush` unchanged; the remaining systems, the flush, or the rest of the flush do not run. The world then is in a failed phase: every later structural change, flush, update and system registration is an `IllegalStateException`; reads still answer but describe an undefined state, which is how "the world is undefined afterwards" (ADR-0030) shows; the loop fails (`REQ-LOOP-010`) and the game discards the world. The phase (idle, updating, flushing, failed) is one `int` field set around the update and the flush with `try`/`finally`, no catch.
10. **Threads and allocation.** Runtime thread only (ADR-0018), as `World`. Measured by `UpdateAllocationTest` with the per-thread allocation counter: 1,000 updates over 1,000 objects, each applying the flags, running four systems (one switching another every step, one iterating a query and adding or removing a trait for every object from inside the iteration, one removing and creating 100 objects with a trait), flushing about 1,300 commands and making 2,998 listener calls to two object and two trait listeners (2,998,000 over the measure), allocate 0 bytes, under the 1 KiB tolerance, after a warm-up of the same steps. Wall-clock time is the benchmark of batch 6 (`REQ-ECS-009`).

## Options considered

- Listener shape: two interfaces with default methods (chosen; a game implements the events it needs, the names of ADR-0034 and `conventions.md`) vs four one-method interfaces (lambdas work, but four registration pairs and verbose names) vs one interface with four methods (a listener of destructions also sees every trait change).
- Trait events: one world-level trait listener with the type ID (chosen; ADR-0034 "registered on the world") vs a listener per storage (cheaper when many types are listened to separately; a compatible addition later).
- Registration during a delivery: copy on write (chosen; simple, the delivery allocates nothing, ADR-0018 holds per event) vs pending add and remove queues applied after the flush (no allocation on registration, but a listener removed during the flush would still receive the rest of it).
- Structural change by a listener: refused (chosen; fail-fast, reversible) vs recorded for the next flush (useful for spawning on destruction, but needs a second log and rules for staged trait instances) vs applied in the same flush (changes the flush while it iterates, contrary to ADR-0011 decision 6).
- System contract: `update(double stepSeconds)` (chosen; one abstract method, the step of ADR-0030) vs `update(World world, double stepSeconds)` (the world is already known to the system that created its queries).
- Enabled flag: requested and applied flags copied at the start of the update (chosen; "applies at the next step" from any caller) vs a flag read when the system's turn comes (a system disabled by an earlier one would stop in the same step).
- Registration during an update: refused (chosen; the order of the current step stays fixed, fail-fast) vs deferred to the next step (a pending list and another rule for its order).
- Invalid step: refused (chosen; ADR-0017 fixed positive step) vs clamped or ignored (hides a loop error).
- Failure: a failed phase refusing later changes (chosen; "undefined" becomes detectable) vs no state (later calls would silently run on a half-applied step).
- Step count: none (chosen; the loop owns it) vs `update` returning a counter (a second source of truth).

## Consequences

- Positive consequences: games and later modules (camera, audio, `multiplayer`, `traits`) react to object and trait changes without polling and without allocation; systems run in a fixed order with game systems between the standard ones; one call per step runs the systems and the flush; misuse inside the update and the flush fails fast.
- Costs / constraints: a listener cannot request structural changes directly; listener registration allocates an array; system lookup is linear in the number of systems; a failed world must be replaced.
- Impact on modules and APIs: `ecs` gains `ObjectListener`, `TraitListener`, `GameSystem`, `World.update`, `addSystem`, `removeSystem`, `setSystemEnabled`, `isSystemEnabled`, `getSystemCount` and the four listener registration methods; `ChangeHook` is removed (package-private); the structural methods document the `IllegalStateException` of the flush and of the failed phase; `examples` gains `SystemExample` with `LaySystem`, `BurnSystem` and `BombTally`; the Android device test `EcsTest` covers events and systems.
- Impact on tests and documentation: unit tests of event order and content, several listeners, registration inside a callback, refusal of structural changes by a listener, listener failure, reproducibility, slot order and ties, game systems between the standard slots, the enabled flag, one flush per update after every system, state stable between updates, invalid steps, misuse inside the update and system failure; an allocation test; `features/ecs.md` (State), `features/README.md`, `traceability.md`, `contracts.md`, `interfaces.md`, `api-index.md`, `engine-features.md`, `roadmap.md`, `agent-workflow.md`.

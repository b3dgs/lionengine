## Context

Batch 3 of the feature page is "cached queries with include/exclude and ID copy". The rules are fixed: a view of the objects having all of an include set of trait types and none of an exclude set, caching its dense list, updated incrementally when traits are added or removed, iterated without allocation (ADR-0011 decision 5); changes requested during an iteration go to the command log (ADR-0030 decision 2); the order is deterministic for the same operation sequence, without identity hashing or `HashMap` iteration, and is not creation order (ADR-0030 decision 9); a query copies its IDs in ascending order into a caller-provided `long[]` without allocating (ADR-0034); the canonical name `Query` (ADR-0037); trait type IDs, masks in words of 64 types and the change hook of ADR-0075 decision 7. The documents leave open the signatures, how the types of a query are named, the iteration form, the state a new query starts from, the capacity of a query and its growth, what an undersized copy buffer does, how the sort avoids allocating, whether a query can be released, and how query maintenance coexists with the hook that the listeners of batch 4 will use.

## Decision

1. **Types and signatures.** `Query`, a public final class, created by the world: `World.createQuery(TraitStorage<?>... include)` (no exclude set) and `World.createQuery(TraitStorage<?>[] include, TraitStorage<?>[] exclude)`; `World.getQueryCount()`. Public members of `Query`: `getCount()`, `getId(int position)`, `copySortedIds(long[] buffer)`. Wildcards appear in parameters only, never in a return type (Sonar S1452).
2. **Types named by their storage handle.** A query names its trait types by the `TraitStorage` handles that `World.register` returned (ADR-0075 decision 2), not by raw `int` type IDs: a handle cannot name an unregistered type and is checked to belong to the world, so a type of another world is refused instead of silently matching the type with the same number. The query keeps only its include and exclude mask words, sized to the highest type ID it names; a type registered after the query is in neither set.
3. **Validation.** `IllegalArgumentException` for a `null` set, a `null` element, a storage of another world, an empty include set (an empty include set would select every object and need the creations and removals of traitless objects; not needed by the feature page, it can be added later without breaking a caller), and a type both included and excluded (the query could never match). A type given twice in a set counts once. Each call creates a new query, even for the same sets: no lookup of an existing query, which would need hashing on the sets.
4. **Iteration.** An index loop from `0` to `getCount()` over `getId(position)`, which allocates nothing: no iterator, no callback. `getId` refuses a position outside `[0, getCount())` with `IllegalArgumentException`. The dense list changes at the flush only, so structural changes recorded inside an iteration (object creation and removal, trait addition and removal) leave the iteration valid: every object listed at its start is visited once (`REQ-ECS-006`). Calling `flush()` inside an iteration is a misuse, documented and not detected.
5. **Incremental update and order.** The world keeps its queries in an array, in creation order. At the flush, each attachment of a trait to an object that had none of the type, and each detachment (trait removal, or object removal, which detaches its traits by ascending type ID), changes the mask bit, then updates every query that includes or excludes that type: the object's mask is tested word by word against the include and exclude words; an object that starts to match is appended to the dense list, one that stops matching is swap-removed. A replacement changes no mask bit and no query. Objects without traits never match, so creations and removals need no query work beyond their traits. The order is thus fixed by the operation sequence (`REQ-ECS-012`): no hashing, no creation-order guarantee, reordered by removals.
6. **Query created after objects exist.** A new query is filled at once from the state of the last flush: it walks the dense list of its include storage with the fewest traits, in its dense order, and appends each object whose mask matches. Pending objects and recorded commands are not seen; the next flush applies them and updates the query like the others.
7. **Capacity and growth.** A query holds a dense `long[]` of IDs and an `int[]` of positions per object index, both sized to the object capacity of the world, the bound of its members: no query capacity to configure, no growth on membership. They grow with the object table (at the flush or by `World.reserve`), never shrink. Memory: 12 bytes per object index per query, 12 KiB per query at the default 1,024 objects.
8. **Sorted copy.** `copySortedIds(buffer)` copies the `getCount()` IDs to the start of the buffer, sorts them ascending in place with a heapsort written in `ecs` (allocation-free and deterministic on every runtime, unlike `Arrays.sort`, whose JDK implementation may allocate a merge buffer for large arrays and whose Android implementation differs), leaves the rest of the buffer unchanged and returns the count. A `null` buffer or one shorter than `getCount()` is refused with `IllegalArgumentException`, the buffer unchanged: a partial copy would silently drop the highest IDs, and the caller sizes its buffer from `getCount()` or the object capacity.
9. **No release.** A query lives as long as its world: there is no method to release it. Queries are created at initialization by the systems that use them; a world belongs to a scene, so its queries go with it. The documentation says that each query adds a constant cost to every trait change of its types at the flush, so queries are created once, not per step. Adding a release later is a compatible addition.
10. **Coexistence with the change hook.** Queries are not maintained through `ChangeHook`: the world updates them itself right after each mask change, and `ChangeHook` stays package-private for the listeners of batch 4. During a hook call the queries agree with the masks: for an addition the hook runs after the update, so the queries list the object; for a removal the hook runs before the mask is cleared (ADR-0075 decision 7, so a listener can still read the trait), so the queries still list it; at the destruction of an object the queries no longer list it. A listener must not change the world (ADR-0075), which also protects the queries.
11. **Threads and allocation.** Runtime thread only (ADR-0018), as `World`. Measured by `QueryAllocationTest` with the per-thread allocation counter: 1,000 steps over 1,000 objects and three queries (one include, two includes, one include and one exclude), each step iterating the queries, recording from inside the iterations about 2,000 trait commands (an excluded trait added or removed, an included one replaced) and 100 object removals and creations with three traits, then flushing and copying the sorted IDs (about 2.5 million commands and 1,000 flushes), allocate 0 bytes, under the 1 KiB tolerance, after a warm-up of the same steps. Wall-clock time is the benchmark of batch 6 (`REQ-ECS-009`).

## Options considered

- Naming the types: storage handles (chosen; typed, checked against the world) vs `int` type IDs (a number of another world, or of a type not yet registered, would be accepted or need a range check only) vs `TraitType` instances (a lookup from type to storage, which ADR-0075 avoided).
- Creation API: two `World.createQuery` overloads (chosen; no new public class) vs a query builder (`include(...)`, `exclude(...)`, `build()`: one more public type and a mutable step) vs one method with two arrays only (a heavier call for the common include-only query).
- Iteration: count plus indexed access (chosen; zero allocation by construction, like the dense accessors of the storages) vs a callback interface (a lambda capture can allocate per step) vs an `Iterator` (allocates or needs a reusable cursor with its own lifecycle).
- Storage of a query: dense list plus per-index positions sized to the object capacity (chosen; O(1) join and leave, no growth on membership) vs a list sized to the smallest include storage (grows with trait capacities, more growth points) vs a bitset rescanned at each flush (O(capacity) per flush and order by index, not incremental).
- Undersized buffer: refusal (chosen; fail fast, nothing hidden) vs copying the smallest IDs that fit (a silent truncation) vs returning the needed length without copying (an error path that looks like success).
- Sort: own heapsort (chosen; in place, no allocation, same result everywhere) vs `Arrays.sort` (allocation not guaranteed absent, implementation differs on Android) vs keeping the list always sorted (O(n) insertion at the flush).
- Release: none (chosen; queries created at initialization, a world per scene) vs `World.removeQuery(Query)` (an extra lifecycle state, accessors of a released query to define) vs `AutoCloseable` (resource warnings on every use).

## Consequences

- Positive consequences: systems iterate exactly the matching objects with an index loop and no allocation; the flush keeps every query up to date in proportion to the trait changes; the order is reproducible, and an explicit ascending copy exists when order matters; the listeners of batch 4 plug into the hook without touching query maintenance.
- Costs / constraints: 12 bytes per object index per query; each query adds a mask test to every change of its types at the flush; queries cannot be released before their world; an empty include set is not supported.
- Impact on modules and APIs: `ecs` gains `Query`, `World.createQuery` (two overloads) and `World.getQueryCount`; `examples` gains `QueryExample` with the trait `Frozen`; the Android device test `EcsTest` covers queries.
- Impact on tests and documentation: unit tests of matching across more than 64 types, incremental update on add, remove, replace and object removal, a query created after objects exist, changes requested inside an iteration, determinism across two runs, the sorted copy with exact, larger and undersized buffers, the in-place sort, growth, validation and the agreement with the hook; an allocation test; `features/ecs.md` (State), `features/README.md`, `traceability.md`, `contracts.md`, `interfaces.md`, `api-index.md`, `engine-features.md`, `roadmap.md`, `agent-workflow.md`.

## Context

Batch 2 of the feature page is "trait registry, pooled storage, deferred add/remove and flush". The rules are fixed: traits are data only, each type registered explicitly once with an `int` type ID, no reflection (ADR-0011 decision 3, ADR-0020); one sparse set per trait type with swap-remove and a per-object bit mask supporting more than 64 types (ADR-0011 decision 4); commands in recorded order, the last wins, an addition followed by a removal both apply and both fire their events (ADR-0030 decision 2); pooled instances in dense arrays, a reset on removal, capacity pre-sized from the configuration, doubling at the flush, never shrinking (ADR-0030 decision 4); 256 instances per trait type by default, configurable at world creation and by `reserve` (ADR-0034); the canonical name `TraitType<T>`, an interface (ADR-0037, `interfaces.md`); trait commands as new kinds of the batch 1 command log, accessors through `checkAlive` (ADR-0074 decisions 4 and 7). The documents leave open the Java signatures, how a typed access finds the storage of a type without reflection or identity hashing (ADR-0030 decision 9), what "replace" is, the instance handed to the caller of an addition, what a command on an object or trait that is gone at the flush does, the order of the changes when an object with traits is removed, the errors, and the form of the seams of queries and events.

## Decision

1. **Types.** `TraitType<T>`, a public interface implemented by the game once per trait type: `T create()` (a new instance in its reset state) and `void reset(T trait)` (back to that state). Two abstract methods, so not a functional interface; a constant anonymous class or a small class is the usual form. `TraitStorage<T>`, a public final class, is the storage of one trait type in one world (the "trait storage" of the feature page); `World.register(TraitType<T>)` is the registry and returns it. Public members: `World.register`, `World.getTraitTypeCount()`; `TraitStorage.add(long)`, `remove(long)`, `has(long)`, `get(long)`, `reserve(int)`, `getTypeId()`, `getType()`, `getCount()`, `getCapacity()`; `WorldConfig(int objectCapacity, int traitCapacity)` with `DEFAULT_TRAIT_CAPACITY` (256) and `MAX_TRAIT_CAPACITY` (2<sup>30</sup>, as many as objects). The masks (`TraitMasks`) and the change hook (`ChangeHook`) are package-private.
2. **Typed access through the storage handle.** Accesses go through the `TraitStorage<T>` returned at registration, kept by the game or its systems in a field: it reaches its dense array directly, with no lookup from a `TraitType` to its storage (a map keyed on the type would hash on identity, which ADR-0030 decision 9 excludes, and costs a lookup per access) and no unchecked cast. The type IDs are `0` for the first registered type, then consecutive in registration order; the `int` is what listeners, masks and queries carry.
3. **Registration.** Explicit, once per type and world: a `TraitType` already registered in the world (the same instance) or `null` is refused with `IllegalArgumentException`; the same instance may be registered in several worlds, each with its own storage and type ID. Registration is allowed at any time outside a flush, also after objects exist (they have no trait of the new type); it allocates the storage and creates `traitCapacity` instances into its pool. A type whose `create` returns `null` fails with `IllegalStateException`, and the world is left unchanged at registration. No limit on the number of types besides memory: masks are words of 64 types, one more word per 64 types.
4. **Additions and replacement.** `add(objectId)` records an addition and returns at once an instance taken from the pool, in its reset state, which the caller fills before the flush; the flush attaches that very instance. An addition on an object that already has a trait of the type replaces it at the flush: the last addition wins, the earlier instance is reset and pooled, the mask and the count are unchanged. "Replace" of the feature page is this case: no separate method, because a call-time check that the trait exists could not be definitive while earlier commands of the same step are still in the log. A replacement is reported as a removal then an addition of the type (decision 7).
5. **Commands on what is gone.** As for a removal recorded twice (ADR-0074 decision 5), the flush ignores what no longer applies: a trait removal on an object without the trait at that point of the flush changes nothing; a trait addition on an object removed by an earlier command of the same flush (created and removed in the step included) is discarded, its instance reset and pooled. An addition followed by a removal both apply: no trait after the flush, both reported. A removal followed by an addition leaves the new trait.
6. **Removal of an object.** The flush removes its traits by ascending type ID, each one reset and pooled, then the object; masks make this cost proportional to the traits it has.
7. **Seams.** `TraitMasks` keeps one bit per type per object index, changed at the flush only, read word by word by the queries of batch 3. `ChangeHook` receives each effective change at the flush, in order, with primitive arguments: created, destroyed `(long)`, trait added, trait removed `(long, int)`; a trait removal is reported before its instance is reset, so a listener of batch 4 can still read it. The default hook does nothing. Commands that change nothing are not reported (`REQ-ECS-012`, "each effective change fires its event").
8. **Errors.** `add` and `remove` accept an alive or pending object and refuse a stale or never-valid ID with `IllegalArgumentException`, recording nothing (the check of `World.remove`). `has` and `get` read the state of the last flush through `checkAlive`: `IllegalStateException` for a pending object, `IllegalArgumentException` for a stale or never-valid ID; `get` on an object without the trait throws `IllegalStateException` (`has` is the check method of `conventions.md`). Messages name the type ID and the object ID; they are built on the failure path only.
9. **Pool and capacity.** Each storage owns its instances: attached ones packed in a dense array (swap-remove), free ones in a pool, those handed out by `add` since the last flush in a staged list; the command records the staged slot in a fourth primitive array of the log. The dense array holds `traitCapacity` traits; the flush first doubles it until the attached and staged traits fit, then applies the commands; `reserve(n)` grows it and fills the pool to `n` instances at once; never shrinks. An addition that finds the pool empty creates an instance, a warm-up allocation like the doubling of the command log; the pool is last-in first-out, so the order of reuse is deterministic (`REQ-DET-001`). The sparse array of each storage and the masks follow the object table when it grows, at the flush or by `World.reserve`.
10. **Threads and allocation.** Runtime thread only (ADR-0018), as `World`. Measured by `TraitAllocationTest` with the per-thread allocation counter: 1,000 steps in which 1,000 objects with two traits are removed (one more addition recorded on each, discarded at the flush), 1,000 objects are created with two traits, and a third trait is added and removed on each (about 7 million commands and 1,000 flushes) allocate 0 bytes, under the 1 KiB tolerance, after a warm-up that grows the object table to 2,048 and the three storages to 4,096, 2,048 and 1,024 (the dense array is sized at the flush for the attached plus the staged traits, here 3,000, 2,000 and 1,000). Wall-clock time is the benchmark of batch 6 (`REQ-ECS-009`).

## Options considered

- Typed access: a storage handle returned by `register` (chosen; direct, typed, no lookup) vs `World.get(objectId, TraitType<T>)` with an identity map from type to storage (identity hashing, a lookup per access) vs an `int` type ID plus a `Class<T>` cast (a cast per access, reflection-adjacent API) vs type IDs stored in the `TraitType` (one ID per type for every world: two worlds could not register types in different orders).
- Instance of an addition: handed out at the call, from the pool (chosen; the caller fills it, object definitions of batch 5 will too) vs created at the flush and filled after it (the trait would exist one flush before its data).
- Replacement: an addition over an existing trait (chosen) vs a separate `replace` method that fails when the trait is absent (the check cannot be definitive before the flush) vs failing an addition over an existing trait at the flush (a failure in the middle of a flush leaves the world half applied).
- Pool storage: `ArrayList` lists pre-sized with `ensureCapacity` (chosen; no unchecked generic array cast, no allocation once sized) vs `Object[]` arrays with casts (unchecked casts are excluded by the build) vs a `T[] newArray(int)` method in `TraitType` (one more method to write per trait type).

## Consequences

- Positive consequences: games define traits with two short methods and access them without lookups; trait and object commands keep one recorded order; no allocation on the steady add, remove, replace and flush paths; the queries and the events of the next batches plug into the masks and the hook without changing the flush.
- Costs / constraints: each registered type pre-creates 256 instances by default (memory proportional to types × capacity, per world); each storage holds an `int` per object index for its sparse array; a trait handed out by `add` before the flush is not yet visible to `get`.
- Impact on modules and APIs: `ecs` gains `TraitType` and `TraitStorage`; `WorldConfig` gains the trait capacity (callers of the one-argument constructor of batch 1 pass both capacities, no backward compatibility is kept, `AGENTS.md`); `examples` gains `TraitExample` with the trait `Fuse`; the Android device test `EcsTest` covers traits.
- Impact on tests and documentation: unit tests of registration, deferred add, remove and replace, accessors, pooling, capacities and growth, a regression set of the mixed flush order with the change hook, an allocation test; `features/ecs.md` (State), `features/README.md`, `traceability.md`, `contracts.md`, `interfaces.md`, `api-index.md`, `engine-features.md`, `roadmap.md`, `agent-workflow.md`.

## Context

Batch 1 of [`../features/standard-traits.md`](../features/standard-traits.md) delivers `Transformable`, `Movable` and the `Movement` system in the module `traits`, which had no type yet. The rules are fixed: traits are data only, `double`, in meters and meters per second (ADR-0014); the position is the object **center** and the size the full width and height (ADR-0034); Y grows up (ADR-0013); the previous position is captured at the step start for interpolation with `alpha`, and extrapolation never feeds the next step (ADR-0017, ADR-0030, decision 8); `Movement` runs at slot 3000, integrates the velocity with the constant step in seconds and clamps the speed (ADR-0034, `REQ-STD-002`); each standard trait documents its bytes per instance, measured as the `ecs` benchmark measures (ADR-0034, ADR-0079); each standard system accepts extra excluded trait types when created (`REQ-STD-011`, ADR-0038); the `ecs` contracts are the ones of ADR-0074 to ADR-0078 (`TraitType`, `TraitStorage`, `Query`, `GameSystem`, `World.addSystem(system, slot)`).

The documents leave open who captures the previous position (the `Movement` system covers only objects with a velocity, and a capture inside `World.update` would change `ecs`), whether the clamp limits the magnitude or each axis, the maximum speed of a new `Movable`, how a game obtains the trait types and gives the systems their storages, whether `REQ-STD-011` comes now or with batch 7, which batch delivers the object definition files of ADR-0032, the class names of the systems (`interfaces.md` asks for distinct names where a system shares a trait's name), the order of clamp and integration, the integration scheme, and the accessors of the traits.

## Decision

1. **Previous-position capture (owner answer).** A separate standard system, `TransformCaptureSystem`, at slot `Integer.MIN_VALUE` (`TransformCaptureSystem.SLOT`), before every other slot: at each step it copies the position into the previous position of every object having a `Transformable` (and no excluded trait), with or without a `Movable`. The previous position is thus the position of the step start whatever system moves the object afterwards, game systems below slot 3000 included. `ecs` is unchanged. Systems of equal slots run in registration order, so a game registers the capture before any system it gives the same slot; a game that does not interpolate may leave the capture out.
2. **Clamp (owner answer).** On the magnitude, direction kept: if `vx² + vy² > maxSpeed²`, the velocity is multiplied by `maxSpeed / sqrt(vx² + vy²)` and stored; a speed equal to the limit is unchanged; a limit of `0` stops the object.
3. **Default maximum speed (owner answer).** A new or reset `Movable` has a zero velocity and a maximum speed of `Double.POSITIVE_INFINITY`, meaning no limit. `setMaxSpeed` refuses a negative value and `NaN` (`IllegalArgumentException`), since the clamp formula needs a value `≥ 0`.
4. **Exposure (owner answer).** Each standard trait class has a public constant `TYPE` (a `TraitType`), shared by every world; a game registers it in each world (`world.register(Transformable.TYPE)`), creates each system with the world and the storages the registration returned, and adds it with the system's public constant `SLOT`: `world.addSystem(new MovementSystem(world, transformables, movables), MovementSystem.SLOT)`. No registration helper and no lookup by type.
5. **Excluded trait types now (owner answer, `REQ-STD-011`).** Both systems have a constructor without excluded types and one taking an array `TraitStorage<?>[] excluded` (possibly empty, not kept), passed as the exclude set of the system's query; an array, not varargs, like `World.createQuery(include, exclude)`. Batch 7 keeps the same form for the later systems.
6. **Object definition files later (owner answer).** Batch 1 registers no factory for `lionengine:transformable` and `lionengine:movable`: the object registry, the factories reading the parameter objects (ADR-0032) and the factories of every standard id come with a separate batch, to be added to the feature pages (`OQ-178`).
7. **Names (owner answer).** Standard system classes take the suffix `System`, so the names stay uniform when a system shares its trait's name (`GravitySystem`, `LifetimeSystem` later): `MovementSystem` and `TransformCaptureSystem`. The trait classes keep the canonical names `Transformable` and `Movable` (ADR-0037).
8. **Movement step.** For each object of its query (`Transformable` and `Movable`, none of the excluded types), `MovementSystem` first clamps the velocity (decision 2), then adds `velocity * stepSeconds` to the position: explicit Euler with the constant step (ADR-0017), the order of the stand-in system of ADR-0079. The result depends only on the trait values and the step, not on the iteration order; `double` arithmetic and `Math.sqrt` are correctly rounded, so platforms agree (`REQ-DET-001`).
9. **Trait accessors.** Fields are private (checkstyle). `Transformable`: `getX`, `getY`, `setPosition(x, y)`, `getWidth`, `getHeight`, `setSize(width, height)`, `getPreviousX`, `getPreviousY`, `setPreviousPosition(x, y)`; the previous position is public so that a game placing or teleporting an object sets it too (otherwise the frames before the next capture interpolate from the old place). `Movable`: `getVelocityX`, `getVelocityY`, `setVelocity(vx, vy)`, `getMaxSpeed`, `setMaxSpeed(maxSpeed)`. Values other than the maximum speed are not checked; the Javadoc states that the game keeps them finite and the size positive or zero. The capture and the translation are package-private operations of the systems. Each system exposes its query (`getQuery()`), for tests and tools.
10. **Bytes per instance.** Measured by `TraitMemoryTest` with the per-thread allocation counter, the method of `StepBenchmarkTest`: 64 bytes per `Transformable` and 40 per `Movable` on the desktop JVM (64-bit HotSpot, compressed class pointers), written in their Javadoc; the test asserts them as upper bounds of the measure rounded to the byte, so a smaller layout passes. The benchmark of `REQ-ECS-009` is not measured again by this batch: by ADR-0079 the batch that delivers the last of `Transformable`, `Movable`, `Gravity` and `Lifetime` (batch 2) replaces the stand-ins and measures.
11. **Allocation.** No allocation per step in either system (one query each, created at construction); `MovementAllocationTest` asserts it over 1,000 steps of 1,000 objects with the 1 KiB tolerance of the `ecs` allocation tests.

## Options considered

- Capture: a capture system at the lowest slot (chosen: every `Transformable`, no `ecs` change) vs inside `MovementSystem` before it integrates (objects without `Movable` never capture; changes by systems below 3000 are folded into the previous position) vs a pre-step hook in `World.update` (an `ecs` API change for one trait).
- Clamp: magnitude (chosen: direction kept, a diagonal is not faster) vs per axis (a diagonal reaches `maxSpeed · √2`).
- Default maximum speed: no limit (chosen: an unset `Movable` moves) vs `0` (an unset `Movable` never moves).
- Exposure: `TYPE` constants and storages passed to constructors (chosen: explicit, like `TraitExample.FUSE`) vs a registration helper holding all storages (a second way to do the same, couples the traits).

## Consequences

- Positive consequences: interpolation is correct for every `Transformable`, moved by `Movement` or by game code; no `ecs` change; the clamp bounds the displacement per step for the collision batches (ADR-0030, decision 6); objects can be kept out of both systems now.
- Costs / constraints: one more system and query per world for the capture; a game must register the capture first among the systems of its slot; placing or teleporting an object means setting its previous position too; no definition files yet.
- Impact on modules and APIs: `traits` (first public types: `Transformable`, `Movable`, `TransformCaptureSystem`, `MovementSystem`; its `maven.javadoc.skip` removed, `REQ-CORE-003`); `examples` depends on `traits` (`MovementExample`, `Flight`); the Android verification runs `TraitsTest`.
- Impact on tests and documentation: `features/standard-traits.md`, `features/README.md`, `contracts.md`, `interfaces.md`, `api-index.md`, `engine-features.md`, `roadmap.md`, `agent-workflow.md`, `traceability.md`, `testing.md`, `android-compatibility.md`, `open-questions.md` (`OQ-178`).

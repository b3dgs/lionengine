## Context

Batch 5 of [`../features/ecs.md`](../features/ecs.md) is the random source. The rules are fixed: randomness of the simulation comes from a seeded generator owned by the world, never from a global source (ADR-0024, decision 1, `REQ-DET-001`); the generator is project code, SplitMix64 expanding the seed into the state of xoshiro256\*\*, integer operations only, neither `java.util.Random` nor `SplittableRandom` (ADR-0031, `REQ-DET-003`); its canonical name is `RandomSource`, in `core` (ADR-0037), where it already exists with `nextLong`, `nextInt(bound)`, `nextDouble` and `nextBoolean`, reused by the audio variant sets with their own generators (ADR-0067); the world configuration carries the random seed (feature page); several worlds coexist, none is a singleton (ADR-0021, `REQ-WORLD-001`); runtime thread only (ADR-0018); listeners must not change the world during the flush (ADR-0077). The documents leave open how the seed enters `WorldConfig`, the default seed, how systems reach the generator, whether and when it can be reseeded, whether a listener may draw, and how independence between worlds is guaranteed.

## Decision

1. **Seed in the configuration.** `WorldConfig` becomes the record `WorldConfig(int objectCapacity, int traitCapacity, long randomSeed)`. The two-capacity constructor `WorldConfig(int, int)` is kept and uses `WorldConfig.DEFAULT_RANDOM_SEED`. Every `long` is a valid seed, `0` included (SplitMix64 never yields an all-zero state), so the seed adds no validation; the capacities keep theirs. The grid cell size of the configuration belongs to collision (`features/standard-traits.md`) and is not added here.
2. **Default seed.** `WorldConfig.DEFAULT_RANDOM_SEED` is `0x4C494F4E` (the ASCII of "LION"), chosen by the owner. It is the same constant as the camera shake default seed of [ADR-0034](0034-camera-and-ecs-defaults-noise-clamp-slots-capacities-events-shapes.md), borrowed on purpose for one engine-wide default; the two stay independent, since a camera's shake noise is another algorithm with its own state. `WorldConfig.DEFAULT` uses it.
3. **Ownership.** Each `World` creates its own `RandomSource` from the configured seed at construction (through the package-private `WorldConfig.createRandomSource()`), keeps it for its whole life and never takes one from outside: no constructor or setter accepts a generator, so two worlds never share one, and drawing from one world never changes the draws of another. `World.getRandomSource()` returns that instance, always the same one, so a system may keep it from its construction.
4. **Determinism.** Two worlds with the same seed and the same sequence of operations and draws give the same numbers, on the JVM and on Android API 21 (integer operations of `RandomSource`; doubles are exact conversions). A system drawing during `World.update(stepSeconds)` therefore gives the same world in two identical runs (`REQ-DET-001`).
5. **Reseeding.** `RandomSource` gains `reseed(long seed)`, chosen by the owner: it restarts the sequence in place, with the state that `new RandomSource(seed)` would have, allocating nothing, so every reference to the generator stays valid; the constructor now calls it. `World.reseed(long seed)` is the checked route: allowed at setup and between two updates (after `update`, after an explicit `flush`), taking effect at once, so the next draw, and the next update, use the new sequence; refused with `IllegalStateException` while an update runs (a system), while a flush runs (a listener) and after a failure, so that one step draws from one sequence. A borrower calling `RandomSource.reseed` directly bypasses that check: it is documented as a misuse, not enforced, since `RandomSource` knows nothing of the world. Uses: a new round, a seed received from a server, a replay.
6. **Listeners may draw.** Drawing is not a structural change, so the rule of ADR-0077 does not refuse it: listeners run synchronously in flush order, so their draws are part of the same deterministic sequence. Systems, listeners, setup code and inbox events (all on the runtime thread) may draw. Rendering and presentation effects must not draw from the world's generator, because their frame count is not the step count; they own theirs (camera shake, audio variant sets). This is documented, not enforced.
7. **Threads and allocation.** Runtime thread only, as `World` (ADR-0018); `RandomSource` is not thread-safe. Measured by `RandomAllocationTest` with the per-thread allocation counter: 1,000 updates, each running a system that draws 1,000 values of each kind (`nextLong`, `nextInt(1000)`, `nextDouble`, `nextBoolean`, 4 million draws over the measure), with a `World.reseed` after every tenth update (100 reseeds), allocate 0 bytes, under the 1 KiB tolerance, after a warm-up of the same steps.

## Options considered

- Seed entry: a third record component with the two-capacity constructor kept (chosen; one canonical constructor, no break for callers) vs a separate setter on the world (the configuration would not describe the world) vs a builder (heavier than the other records of the engine).
- Default seed: `0x4C494F4E` (chosen by the owner) vs `0` vs the `RandomExample` seed `2026`.
- Reseeding: `RandomSource.reseed` in place, checked by `World.reseed` (chosen by the owner; references stay valid, no allocation) vs the world replacing its instance (a system keeping the old reference would silently draw from a dead sequence) vs no reseeding (a new world per seed; simplest, but a new round would rebuild every storage and query).
- Reseeding during an update: refused (chosen; one sequence per step, fail-fast, reversible) vs taking effect at the next update (a pending seed and one more rule).
- Listener draws: allowed (chosen; deterministic in flush order, nothing to enforce) vs refused (cannot be enforced without wrapping the generator, for no determinism gain).
- Access: the same `RandomSource` instance (chosen; the existing core type, no wrapper, no allocation) vs a world-specific read-only view (a second type with the same methods).

## Consequences

- Positive consequences: systems draw reproducible numbers from the world without global state; replays, rounds and server-given seeds are possible without rebuilding the world; worlds stay independent.
- Costs / constraints: a direct `RandomSource.reseed` by a borrower and draws from rendering are not detected; the record `WorldConfig` gains a component, so its canonical constructor and `equals` change.
- Impact on modules and APIs: `core` gains `RandomSource.reseed(long)`; `ecs` gains `WorldConfig.randomSeed()`, `WorldConfig.DEFAULT_RANDOM_SEED`, the three-argument `WorldConfig` constructor, `World.getRandomSource()` and `World.reseed(long)`; `examples` gains `RandomSpawnExample` with the system `SpawnSystem` and the trait `Spot`; the Android device tests `CoreTest` (`testRandomReseed`) and `EcsTest` (`testRandomSource`) cover them.
- Impact on tests and documentation: `RandomSourceTest.testReseed`; `WorldConfigTest` (default seed, the two-capacity constructor, any seed, validation with a seed); `WorldRandomTest` (default and custom seed, reference vectors of `RandomSourceTest`, independent worlds, reseeding at setup and between updates, refused during an update, a flush and after a failure, listener draws, a system drawing during the update reproducible across two runs); `RandomAllocationTest`; `RandomSpawnExampleTest`; `features/ecs.md` (State), `features/core-foundation.md`, `features/README.md`, `traceability.md`, `contracts.md`, `interfaces.md`, `api-index.md`, `engine-features.md`, `roadmap.md`, `agent-workflow.md`.

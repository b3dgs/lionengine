## Context

Batch 5 of [`../features/standard-traits.md`](../features/standard-traits.md) delivers the `Jump` system. The rules are fixed: the system applies the impulse on a jump request when grounded, within the coyote time, or when a buffered request meets the ground; on an early release while ascending it multiplies the upward velocity by the cut factor when the variable height is enabled (`REQ-STD-004`; ADR-0030, decision 7; ADR-0034, cut factor `0.5`); the impulse is positive with Y up (ADR-0013); the slot is 1000, before `Gravity` 2000, `Movement` 3000, `Collision` 4000 and `Lifetime` 5000 (`REQ-STD-008`, ADR-0034); each standard system takes excluded trait types (`REQ-STD-011`); `grounded` is written by the tile push-out of `CollisionSystem` at slot 4000, so the `Jump` system reads the flag of the previous step (ADR-0083); game inputs go through `input-api` actions, and `traits` depends only on `ecs`, `physics` and `core` (`REQ-MP-002`, [`../architecture/modules.md`](../architecture/modules.md)). Batch 4 brought `Jumpable` forward as data, 48 bytes per instance.

The documents leave open how a jump request and its release reach the system without an input dependency and who clears a consumed request, where the coyote and buffer timers live, their reset values and whether they are readable, the exact window rules, whether the impulse replaces or adds to the vertical velocity, whether the jump clears `grounded`, how often a jump can be cut, which objects the system processes, and whether this batch delivers the full pipeline test of `REQ-STD-008`.

## Decision

1. **Request (owner answer).** `Jumpable` gains a jump held flag (`isJumpHeld`, `setJumpHeld`), written by the game at each step from its jump action, by a game system below slot 1000 (input and intent, ADR-0034). The `Jump` system keeps the value of its previous step in a private field: held now and not before is a **press**, held before and not now a **release**. Nothing has to be cleared by the game; holding the jump never jumps again on landing, only a new press does. `traits` gains no input dependency.
2. **Timers (owner answer).** `Jumpable` gains the coyote and buffer times remaining, in seconds, readable (`getCoyoteRemaining`, `getBufferRemaining`) and written only by the `Jump` system, both `0` in the reset state. The coyote time remaining is set to the coyote time at each step of the system that sees the object grounded, and counted down by the step (never below `0`) at each step that does not: the coyote time starts at the last step seen grounded. A press sets the buffer remaining to the jump buffer and requests a jump in the same step; without a press, the buffer remaining is counted down by the step (never below `0`) and a jump is requested while it stays above `0`.
3. **Jump (owner answer).** A requested jump is applied if the object is grounded or its coyote time remaining is above `0`: the vertical velocity of the `Movable` is **replaced** by the impulse (the horizontal velocity is kept), `grounded` is cleared, and both times remaining are set to `0`, so each window is consumed once and no second jump happens in the air. A buffered press meets the ground at the first step of the system that sees `grounded`, the step after the collision landed the object (the system runs before the collision of its step). A press with a jump buffer of `0` still jumps when grounded or within the coyote time.
4. **Cut (owner answer).** A jump can be cut from the step it is applied. On a later release, if the variable height is on and the vertical velocity is above `0` (ascending, the impulse being positive with Y up), the vertical velocity is multiplied by the cut factor. A release, or a step that sees a vertical velocity at or below `0`, ends the jump that can be cut, so the cut applies at most once per jump and never to a descending object.
5. **Objects (owner answer).** `JumpSystem` processes the objects having `Movable` and `Jumpable` and none of the excluded types given at creation (`REQ-STD-011`): constructors `(world, movables, jumpables)` and `(world, movables, jumpables, excluded)`, one query exposed by `getQuery()`, as `GravitySystem`. An object without `Movable` is skipped; no `Transformable` or `Collidable` is needed. An object outside the query keeps its jump state unchanged.
6. **Scope (owner answer).** The unit tests run `Jump`, `Gravity`, `Movement` and the tile push-out of `Collision` at their slots at steps of 1/30, 1/60 and 1/120 s; the full pipeline integration test of `REQ-STD-008`, with `Lifetime` and a controllable clock, stays batch 6.
7. **Windows in steps.** Times count in steps of the system: with a window `w` and a step `dt`, a jump is accepted at the `k`-th step after the last grounded step (coyote) or after the press (buffer) while `w - k * dt`, computed by repeated `double` subtraction, stays above `0`. A window that is an exact multiple of the step may accept one more step when the subtraction leaves a remainder (as the expiry of `Lifetime`, ADR-0081); the tests use windows of a whole number of steps plus a half.
8. **Logic placement.** The rules are a package-private method of `Jumpable` (`update(velocityY, stepSeconds)`, returning the new vertical velocity), called by `JumpSystem` for each object, as `Gravity.accelerate` is called by `GravitySystem`; the previous held value and the "can be cut" flag are private fields of `Jumpable`, reset with it. The step logic allocates nothing.
9. **Bytes per instance.** With the five new fields (two `double`, three `boolean`), `Jumpable` takes 72 bytes per instance on the desktop JVM (64-bit HotSpot, compressed class pointers), measured by `TraitMemoryTest`, written in its Javadoc and asserted as an upper bound; the 48 bytes of ADR-0083 described the batch 4 data only.
10. **Benchmark.** The benchmark scenes are unchanged: the hop of `TileBenchmarkWorld` keeps setting the velocity itself, so the recorded trend values stay comparable; the steady step of the `Jump` system is checked by `JumpAllocationTest` (1,000 objects pressing, holding and releasing on a tile floor, 1,000 measured steps, 1 KiB tolerance).

## Options considered

- Request: a held flag with edge detection (chosen: one value the game copies from its action, nothing to clear, fits input frames and replay) vs request and release methods with one-shot flags cleared by the system (a lost request when the system is disabled or the object excluded) vs both (two ways to do one thing).
- Timers: readable runtime fields (chosen: the game can show or test the windows) vs hidden fields (no way to check a window from the game).
- Impulse: replacing the vertical velocity (chosen: the same jump height inside the coyote time, while falling) vs adding to it (a weaker jump after a few steps of fall).
- Cut: once per jump while ascending (chosen) vs at every release while ascending (a second press and release in the air would cut again).

## Consequences

- Positive consequences: platform games get the standard jump with coyote time, jump buffer and variable height from the traits, deterministic and allocation-free (`REQ-DET-001`); the game only writes the held flag from its input action.
- Costs / constraints: the game must write the held flag before slot 1000 at every step; a buffered press jumps one step after the landing step; `Jumpable` grows from 48 to 72 bytes; the system's private state (the previous held value, the jump that can be cut) is not readable yet, which a later replication batch would need to expose.
- Impact on modules and APIs: `traits` gains `JumpSystem` and, in `Jumpable`, `isJumpHeld`, `setJumpHeld`, `getCoyoteRemaining` and `getBufferRemaining`; `examples` gains `JumpExample`, `Jumping` and `Ledge`; the Android verification extends `PhysicsTest`.
- Impact on tests and documentation: `features/standard-traits.md`, `features/README.md`, `contracts.md`, `interfaces.md`, `api-index.md`, `engine-features.md`, `roadmap.md`, `agent-workflow.md`, `traceability.md`, `testing.md`, `android-compatibility.md`, `glossary.md`.
